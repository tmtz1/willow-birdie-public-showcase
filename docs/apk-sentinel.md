# APK Sentinel

## Deterministic Android APK triage

APK Sentinel is a private, in-development Willow & Birdie project for evidence-backed static analysis of Android application packages.

The intended product is a bounded API workflow: submit one APK, receive a versioned JSON triage report, and keep the analysis repeatable for the same APK, analyzer version, and rules version.

## Planned analysis areas

- APK identity and package metadata
- Permissions and dangerous permission combinations
- Exported Android components
- Signing certificate metadata and fingerprints
- Bounded URL, domain, and IP extraction
- Suspicious API indicators with evidence references
- Structured findings with severity and category
- A deterministic rule-based risk score

## Safety model

The current product boundary is static analysis only:

- APKs are not installed, executed, or side-loaded
- No dynamic analysis is part of the current MVP
- Uploaded samples and derived artifacts are intended to be ephemeral
- Work is bounded by file-size, extraction, output, and wall-time limits
- The analyzer is designed to run in a restricted, networkless job boundary
- Extracted URLs are treated as inert report data and are not fetched
- The risk score is rule-based; it is not generated by an LLM

Dynamic execution, public ingress, and production payment flows remain separately gated work. The project is not claiming that static analysis can prove an APK safe or malicious.

## Product direction

The planned audience includes security analysts, threat-intelligence teams, malware researchers, and automated pipeline operators who need fast, repeatable APK triage without installing untrusted software.

The x402 payment path is a future product phase, not a claim that a public paid endpoint is currently operating.

## Status

Private and in development. The production implementation, test fixtures, threat-model evidence, and deployment controls remain restricted. This public page describes the research and product direction without exposing implementation details or submitted artifacts.

## Update — human-assisted API access

The planned workflow is now available to human operators through the live API. A person can submit one APK with `curl`, Postman, or another standard HTTP client, follow the x402 payment requirements, resubmit the paid request, and poll the asynchronous result. This is API access for a human operator—not a browser upload portal.

The existing endpoint, price, Base Sepolia network, static-only analysis boundary, and bounded retention behavior remain unchanged. The report is triage evidence and must not be treated as proof that an APK is safe or malicious.

### Hard lesson learned

The paid API contract is asynchronous: a successful submission returns `202 queued`, not the final report. Clients must retain the job ID and result token and poll the result endpoint. Operational readiness matters too: the worker correctly fails closed when its container runtime is unavailable, even when the API and payment path are healthy.
